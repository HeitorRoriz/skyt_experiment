\title[SameEval: Structural Repeatability of LLM Code]{SameEval: A Structural Repeatability Benchmark for LLM Code Generation}

\renewcommand{\shortauthors}{Anonymous Author(s)}
\renewcommand{\shorttitle}{SameEval: Structural Repeatability of LLM Code}

\begin{abstract}
Code-generation benchmarks ask whether a program passes tests, not whether
regenerating from the same prompt yields the same code.
This matters wherever generated code is reviewed, audited, or placed under
change control, and most sharply in safety-critical embedded development,
where teams expect regeneration to reproduce the same code and standards
require confidence in the tools that generate it.
We present \sameeval{}, an overlay that measures structural repeatability on
an existing benchmark: \sameat{} estimates the probability that two
independent generations both pass and share a canonical-form fingerprint.
On all 164 HumanEval+ tasks with four models at two temperatures
(26{,}240 generations), Plus pass is 86.4\% but \sameat{} is 67.7\%; a fifth
model at provider-default sampling passes 92.9\% of the time yet produces the
same code in only 66.3\% of pairs.
Raising temperature from 0 to 0.7 lowers \sameat{} by 11.0 to 28.0 points,
while Plus pass changes by at most 0.8 points (every 95\% CI within
$\pm$2.4), and two models with indistinguishable pass
rates differ by 15 points in repeatability among passers.
Two engineers ($\kappa{=}0.41$ with each other) judged 63 and 64 of the 64 fingerprint-same pairs to be the same implementation, but also called many structurally different passing pairs the same: models agree on the approach more
than on the code.
Form diversity shows no detectable association with hidden-test failure within a task
(exploratory).
\sameeval{} also separates mitigation policies: on held-out generations,
\skyt{}, which regenerates and then substitutes a stored verified function,
raises \sameat{} by 17.0 points, while replaying a stored program remains the
ceiling on static prompts.
We distill the study into an eight-step protocol for measuring and reporting
structural repeatability on any benchmark with an executable oracle, with
each step backed by evidence from this study.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Correctness benchmarks for LLM code generation---HumanEval~\cite{chen2021evaluating},
MBPP~\cite{austin2021program}, SWE-bench~\cite{jimenez2024swebench}---ask whether
\emph{a} generated artifact passes tests.
Production pipelines regenerate: CI retries a generator, an agent re-samples
after a failed test, and two developers issue the same prompt.
Tests cannot tell two passing regenerations apart, yet the artifacts can
differ in structure~\cite{ouyang2023llm}, and every structural difference
reaches a diff, a review, or an audit trail.

This paper's primary contribution is \textbf{\sameeval{}}, a benchmark overlay
that measures that scatter.
It ships no new prompts and no new tests.
It adds a form report on top of an existing task set.
The report's headline is \sameat{}: the probability that two independent draws
both certify and have the same canonical-form fingerprint.
A second column, \sameatc{}, asks the same identity question among passers
only; configs with fewer than two passers are dropped from that column and the
drop is reported.
Throughout, \emph{same form} means identical fingerprints
(Section~\ref{sec:sameness}); \emph{same implementation} means an engineer's
judgment (Section~\ref{sec:human-setup}).

We apply \sameeval{} to all 164 HumanEval+~\cite{liu2023evalplus} tasks at
protocol $N{=}20$: four models at two temperatures plus one at
provider-default sampling (29{,}520 generations / 1{,}476 configs), and ask
four questions.

\begin{enumerate}
  \item \textbf{RQ1.}
        How far apart are functional correctness and repeatability on
        HumanEval+?
  \item \textbf{RQ2.}
        Does \sameat{} measure what it claims, and does it tell us something
        pass@$k$ does not?
  \item \textbf{RQ3.}
        Does repeatability carry information about hidden-test correctness?
  \item \textbf{RQ4.}
        Can \sameeval{} separate mitigation policies, and where do their
        effects come from?
\end{enumerate}

\paragraph{Contributions.}
\begin{enumerate}
  \item \sameeval{}: the \sameat{} / \sameatc{} estimators, with failures in
        the denominator, and a versioned canonical-form fingerprint.
  \item A measurement and reporting protocol for structural repeatability:
        eight task-agnostic steps, from sampling to evaluating mitigations
        on held-out generations with hidden tests reserved, each backed by
        evidence from this study (Section~\ref{sec:protocol-steps}).
  \item Validity evidence: engineers agree with the fingerprint's ``same''
        (63 and 64 of 64 pairs; specificity 98--100\%); three computational
        rulers preserve the gap; \sameat{} separates models that pass@$k$
        cannot; and ten generations per configuration suffice (split-half
        $r_{10}{\ge}0.89$).
  \item Empirical findings: on HumanEval+, Plus pass is 86.4\% but \sameat{}
        is 67.7\%; temperature lowers \sameat{} while Plus pass moves by at most 0.8 points (every CI within $\pm$2.4); generation
        can be repeatably wrong, so \sameat{} is not a proxy for hidden-test
        correctness (exploratory); and among mitigation policies, a stored
        program is the ceiling on static prompts while the lift of \skyt{}~\cite{roriz2026skytmsr} comes
        from canonical substitution.
  \item An artifact with all generations, the scorer, a protocol checklist,
        and recompute commands (Data Availability).
\end{enumerate}

Ouyang \etal{}~\cite{ouyang2023llm} document non-determinism in code
generation.
\sameeval{} adds a standardized pairwise estimator with failures in the
denominator, certification conditioning, a fingerprint whose ``same'' calls
engineers accept, and a protocol for evaluating mitigations.

\paragraph{Not in this paper.}
We do not score by pass@$k$ or by match to the HumanEval canonical solution.
We do not treat copying the first passer as the \skyt{} policy; we \emph{do}
report it as a cache baseline (Section~\ref{sec:rq4}).
This study is Python HumanEval+, not an embedded or safety-certification
evaluation.
A regeneration track under perturbed contexts is future work
(Section~\ref{sec:conclusion}).

\paragraph{Outline.}
Section~\ref{sec:motivation} states the measurement problem;
Section~\ref{sec:related} places \sameeval{} in context;
Section~\ref{sec:protocol} defines the overlay;
Section~\ref{sec:setup} pins the runs, the human study, and the held-out split;
Section~\ref{sec:results} answers the four questions;

Sections~\ref{sec:discussion}--\ref{sec:implications} interpret the results;
Section~\ref{sec:threats} states threats; Section~\ref{sec:conclusion}

\section{Motivation}
\label{sec:motivation}

Regeneration is how LLM-assisted development actually works.
Correctness benchmarks record whether \emph{a} sample
passes~\cite{chen2021evaluating,liu2023evalplus}.
They do not record whether the next passing sample is the same code.
Two shortcuts look as if they dissolve that question.

\paragraph{Why not copy the first passer?}
That is a policy for what to ship, not a measurement.
Keeping one passing program says nothing about whether the next
regeneration would match it; estimating that requires the other draws,
which copy-first discards.
Where regeneration can be avoided, copy-first is a legitimate policy, and
we evaluate it as a cache baseline (Section~\ref{sec:rq4}); on static
prompts it is the repeatability ceiling.
But pipelines and agents regenerate.
Caching eliminates regeneration; \skyt{} constrains it; \sameeval{}
measures what happens when regeneration occurs.

\paragraph{Why not stop calling the model after the first passer?}
That estimates pass@$1$.
\sameat{} is a pairwise rate; it is unidentified if sampling stops at one
success.
Agents are not one-shot samplers on a frozen prompt: they re-issue prompts
across retries, refactors, new files, other developers, and model updates.

\paragraph{Where repeatability is most critical.}
Repeatability matters most where generated code becomes evidence.
Model-based embedded development is the clearest case: engineers specify
behavior in models (for example, in Simulink) and generate production code
from them.
Teams expect the same model and generator configuration to yield the same
code: generated code is reviewed, tested, and traced to requirements once, and
regeneration is expected not to invalidate that evidence.
Functional-safety standards make the dependence explicit.
ISO~26262 requires confidence in any software tool, including a code
generator, that could introduce an error into safety-related
software~\cite{iso26262part8}, and avionics has a dedicated standard for tool
qualification~\cite{rtca2011do330}.
An LLM that returns structurally different code on each regeneration breaks
that expectation even when every version passes its tests: review evidence,
traceability links, and change-control baselines must be re-established after
each regeneration.
In these workflows, structural repeatability is a prerequisite for using
LLM-generated code, not a matter of style.
This paper measures it; it does not evaluate embedded code or tool
qualification (Section~\ref{sec:threats}).

\paragraph{Why structure matters even when behavior agrees.}
Commercial APIs are not bit-deterministic at
$T{=}0$~\cite{ouyang2023llm}.
Batch-invariant inference can remove that source of
variation~\cite{he2025nondeterminism}, but it does not address sampling at
$T{>}0$, where structural variation is largest (Section~\ref{sec:rq1}).
Tests treat two passers as interchangeable.
Artifacts that operate on code structure do not: a diff shows every changed
line, a reviewer of a change inspects that diff, and audit, change-control,
and reproducible-build processes record the code itself, not its behavior.
Whether an engineer would call two passing programs the \emph{same
implementation} is a separate question, which we measure directly
(Section~\ref{sec:rq2}).

\section{Related Work}
\label{sec:related}

\paragraph{Functional correctness.}
HumanEval~\cite{chen2021evaluating}, MBPP~\cite{austin2021program}, and
SWE-bench~\cite{jimenez2024swebench} score pass@$k$ against tests.
HumanEval+~\cite{liu2023evalplus} keeps the same 164 prompts and adds a
larger extra suite.
These protocols do not report how often independent draws share structure.

\paragraph{LLM variability.}
Ouyang \etal{}~\cite{ouyang2023llm} document non-determinism in code
generation, including that $T{=}0$ is not bit-deterministic on commercial
APIs; temperature changes output diversity~\cite{zhu2024hot}.
ReCode~\cite{wang2023recode} perturbs \emph{prompts} and asks whether pass
rate holds.
\sameeval{} leaves the prompt fixed and asks whether two answers are the same
code.
Studies of developer interaction~\cite{vaithilingam2022expectation,barke2023grounded}
treat a generation as a single artifact.

\paragraph{Clones and diffs.}
Fingerprint identity is closer to clone measurement than to
pass@$k$~\cite{roy2009clone}.
AST differencing~\cite{falleri2014gumtree} produces an edit script between two
trees; Zhang--Shasha tree-edit distance~\cite{zhang1989simple} is a related
numeric judge.
\sameeval{} asks how often independent regenerations land on the same
canonical form.
It is not a clone detector, not observational equivalence, and not algorithm
identity.

\paragraph{Selection and repair versus overlay.}
Program repair with language models patches failing
code~\cite{xia2023apr}.
Copying the first passer, clustering by input--output behavior as in
AlphaCode~\cite{li2022alphacode}, execution-guided minimum Bayes-risk
selection~\cite{shi2022mbrexec}, test-driven selection as in
CodeT~\cite{chen2023codet}, and self-consistency-style
agreement~\cite{wang2023selfconsistency} are policies for what to keep.
None of them reports the pairwise form rate of the raw draws.
Consensus over execution behavior is known to track correctness
(AlphaCode clustering; MBR-exec~\cite{shi2022mbrexec}); we find that consensus
over structural form, among programs that already pass, does not
(Section~\ref{sec:rq3}).
Rewriting toward a stored verified form~\cite{roriz2026skytmsr} is likewise a
policy.
That earlier work reported repeatability relative to a first-compliant
anchor; anchor-relative rates cannot distinguish a tight cluster from scatter
around an unrepresentative first draw.
\sameat{} is anchor-free and replaces that measure here.

\sameeval{} is not entropy, output variance, pass@$k$, or duplicate counting.
It estimates the probability of repeated agreement under a chosen
equivalence relation, with failures remaining in the \sameat{} denominator.

\section{\sameeval{}}
\label{sec:protocol}

\subsection{Inputs and regenerations}
A \emph{task} supplies a prompt and a behavioral oracle (unit tests).
A \emph{config} is one task $\times$ one model $\times$ one temperature.
For each config we draw $N$ independent generations; the protocol uses
$N{=}20$.

\subsection{Certification}
\label{sec:certification}
We distinguish three test suites: \textbf{Base}, the original HumanEval unit
tests; \textbf{Extra}, the additional EvalPlus tests; and \textbf{Plus}, the
full HumanEval+ suite (Base and Extra).
On the overlay, \emph{certified} (Plus pass) means the fingerprinter parses
the program and the Plus tests pass.
Unparseable code cannot certify but stays in the \sameat{} denominator.

\subsection{Structural sameness}
\label{sec:sameness}
Two generations are the \emph{same form} iff both parse and their
canonical-form fingerprints match.
The canonical form: parse to an AST; strip leading docstrings from every
module, function, and class body; $\alpha$-rename bound parameters and locals
when the task's naming policy is flexible (free names stay); unparse so the
tree and the source agree; hash \texttt{ast.dump} of that tree.
Literals and statement order are not normalized.
Fingerprint identity is not semantic equivalence (Section~\ref{sec:threats}).

\subsection{Population measures}
\label{sec:measures}
Let a config have $N$ generations and write $C(N,2)$ for the unordered pairs.

\begin{enumerate}
  \item \textbf{\sameat{}} (primary): the fraction of pairs in which both
        generations are certified and have the same form,
        \[
          \texttt{same@2}
          \;=\;
          \frac{\#\{\{i,j\}\,:\,\text{both certified and same form}\}}{C(N,2)}.
        \]
        It is a U-statistic of order 2, keeps failures in the denominator,
        and is defined on every config.
  \item \textbf{\sameatc{}} (secondary): the same identity check restricted to
        pairs of certified generations; undefined when fewer than two
        generations certify, and those configs are omitted from its mean with
        the omission reported.
\end{enumerate}

We always report \sameat{}, \sameatc{} (with the drop count), and pass rate
together.
Reporting \sameatc{} alone is misleading: it can rise when the pass rate falls.
Pairs within a config share generations and are not independent trials, so
inference aggregates one score per task and uses a cluster bootstrap
(10{,}000 resamples, seed 20260723).

\section{Experimental Setup}
\label{sec:setup}

\subsection{Tasks, models, and scoring}
Prompts are the 164 HumanEval tasks; the oracle is the HumanEval+
suite~\cite{liu2023evalplus} (\path{evalplus==0.3.1}, HumanEvalPlus
\texttt{v0.1.10}; dataset hash in Data Availability).
The T-grid models are GPT-4o-mini, Claude Sonnet 4.5
(\path{claude-sonnet-4-5-20250929}), Claude Haiku 4.5
(\path{claude-haiku-4-5-20251001}), and GPT-6 Luna (\path{gpt-6-luna},
reasoning effort \texttt{none}), each at $T\in\{0.0,0.7\}$
(26{,}240 generations / 1{,}312 configs).
$T{=}0$ is the lowest-variance setting a user can choose, and it is still not
deterministic; $T{=}0.7$ is a common sampling setting within the range used in
code-generation evaluation~\cite{chen2021evaluating}.
Claude Sonnet 5 (\path{claude-sonnet-5}) accepts no sampling parameters and
runs with adaptive thinking by default; we score it at provider-default
sampling (3{,}280 generations / 164 configs), which is the setting its users
cannot change.
447 of its 3{,}280 responses contained thinking blocks, which were excluded
from the extracted programs.
Its output budget was 16{,}000 tokens (2{,}048 for the other models); one
response exceeded 2{,}048 output tokens, so the larger budget affected at most one of 3{,}280 responses (thinking tokens included).
Expansion generations used the Batch API; the original two models were called
synchronously.
Returned identifiers:
GPT-4o-mini (alias; generated 17--18 September 2026);
Claude Sonnet 4.5 \path{claude-sonnet-4-5-20250929} (generated 16--18 September 2026);
Claude Haiku 4.5 \path{claude-haiku-4-5-20251001} (generated 24--25 September 2026);
GPT-6 Luna \path{gpt-6-luna} (alias; generated 24--25 September 2026);
Claude Sonnet 5 \path{claude-sonnet-5} (alias; generated 24--25 September 2026).
Completions are stitched onto the prompt and scored in network-disabled
Docker; untrusted code is never executed on the host.
Fingerprints use \texttt{relation\_version}=2.

\paragraph{Inference.}
Pooled estimates are task means: each task contributes the mean of its
model$\times$temperature cells, and tasks are weighted equally.
Intervals are 95\% percentile bootstrap intervals that resample whole tasks
with replacement (10{,}000 resamples, seed 20260723).
Cells where \sameatc{} is undefined are dropped, so a task averages its
defined cells.
Paired differences (between models, or $T{=}0.7$ minus $T{=}0.0$) are formed
per task before resampling, over tasks where both sides are defined.

\subsection{Human study}
\label{sec:human-setup}
Two engineers independently labeled 128 pairs of raw overlay programs,
sampled from the GPT-4o-mini and Claude Sonnet 4.5 cells: 4 model$\times$T
cells $\times$ 4 strata (fingerprint same/different $\times$ both certified or
not) $\times$ 8 pairs, hence 64 fingerprint-same and 64 fingerprint-different
pairs by construction.
Annotator A is a software and electrical engineer with more than 25 years of
experience and is the first author of this paper.
Annotator B is an embedded software engineer with more than 25 years of
experience.
Each saw only the two programs and this question:
\emph{``Would these two programs be treated as the same implementation for
code review, verification, maintenance, or change-control purposes?''}
Model, temperature, test outcomes, and the fingerprint verdict were hidden.
The fingerprint was not modified after labeling.
The sample is stratified on the fingerprint verdict, so unweighted
sensitivity, specificity, precision, and F1 are sample metrics.
Population sensitivity, specificity, and PPV reweight each stratum by its
share of parseable within-configuration pairs in the four annotated cells.
Cohen's $\kappa$ below is a sample $\kappa$ on this design-balanced set.
No repaired (post-\skyt{}) programs were labeled.

\subsection{Exploratory analysis (RQ3)}
We ask whether form diversity among Base-passing programs carries information
about Extra-test failure beyond the Base pass rate.
The analysis was pre-specified on the original overlay, in a dated analysis plan included in the artifact; the replication uses
all five models (1{,}476 configurations, including Sonnet 5).
Forms are fingerprint classes computed only on Base-passers.
A program's modal form is the largest class among the other Base-passers in
its configuration (leave-one-out); ties are unclassified.
$D_c$ is one minus Base-certified \sameat{}; $F_c$ is the Extra-failure rate
among Base-passers.
Extra outcomes never define forms, modes, or $D_c$.
Configurations with fewer than two Base-passers are excluded.

\paragraph{Claim status.}
Confirmatory: the RQ1 gap; RQ2 human agreement (pre-specified protocol) and
rank comparison (pre-specified decision rule); RQ4 held-out $\Delta$\sameat{},
certified disagreement, and temperature interaction.
Descriptive: RQ2 reliability.
Exploratory: RQ3 (pre-specified on the original overlay; five-model
replication).
Post hoc: the paired temperature CIs in Table~\ref{tab:temperature}; the
prevalence-reweighted human rates in Section~\ref{sec:rq2}; the
implementation-level estimate in Section~\ref{sec:discussion}; the diff-cost
summary in Section~\ref{sec:rq1}; the RQ3 uniformity check in Section~\ref{sec:rq3}; and RQ4 case
examples.

\subsection{Held-out split for RQ4}
\label{sec:heldout-setup}
\skyt{} selects a Certified Consensus form from certified train generations
and repairs later programs toward that stored form, rolling back if the
operational oracle fails; if no train generation certifies, repair is skipped.
On the frozen overlay of the two original models we replay the policy without
new language-model calls.
For each of the 656 cells we draw 20 balanced 10/10 splits (seed 20260723),
select the canon on the train 10 only, and repair the test 10.
\sameat{} and \sameatc{} are U-statistics on the test 10 ($C(10,2){=}45$
pairs), averaged over splits.
Paired effects $\Delta{=}\mathrm{post}{-}\mathrm{pre}$ use the paired cluster
bootstrap by task.
The headline design uses only Base tests during canon selection, repair, and
rollback, and reserves Extra tests for final evaluation.
A robustness run (Section~\ref{sec:rq4-robustness}) also uses Plus tests
during repair.

\paragraph{Temperature moves repeatability, not pass rate.}
Table~\ref{tab:temperature} contrasts $T{=}0.7$ with $T{=}0.0$ per model.

\subsection{RQ2: Validity of the measure}
\label{sec:rq2}

\paragraph{Human agreement.}
Table~\ref{tab:human} compares each annotator, and their consensus, with the
fingerprint.
Of the 64 fingerprint-same pairs, A judged 63 and B all 64 to be the same
implementation; the single exception is a pair of byte-identical files that A
labeled different (reported as labeled).
Conversely, whenever an engineer judged two programs different, the
fingerprint almost always did too (specificity 97.9\% for A, 100\% for B).
No pair exists where the fingerprint says same and both engineers say
different.
The fingerprint's ``different'' is stricter than either engineer on the
unweighted sample: sensitivity is 77.8\% (A) and 63.4\% (B), and 84.0\% on
the 96 pairs where they agree.
The engineers themselves agree on 75\% of pairs (sample $\kappa{=}0.41$,
95\% CI 0.26--0.55), fair to moderate agreement, and they disagree mostly
where the fingerprint says different and both programs pass (18 of their 32
disagreements).
The pairs both engineers still call the same implementation are mostly two
passing programs that differ by a small rearrangement, such as two reordered
assignments.
Reweighting each stratum by its share of parseable within-configuration pairs
in the four annotated cells raises sensitivity to 93.1\% [89.7, 96.4] for A
and 83.2\% [80.9, 85.9] for B, with specificity 98.2\% [94.2, 100] and 100\%,
and PPV 99.6\% [98.7, 100] and 100\%; B's two 100\% rates have no disagreements to resample, so their bootstrap intervals are degenerate.
These reweighted rates are post hoc.
The fingerprint is therefore a precise but conservative ruler: its ``same''
is one engineers accept, and its ``different'' includes variation that
engineers weigh differently.

\subsection{RQ3: Repeatability and hidden-test correctness}
\label{sec:rq3}

The analyses below were pre-specified on the original overlay and are
exploratory; the five-model pool (1{,}476 configurations, including Sonnet 5)
is a replication, and the uniformity check is post hoc.

On the original overlay, form diversity carried no detectable signal
about hidden-test failure beyond the pass rate (Table~\ref{tab:diversity-signal}, Figure~\ref{fig:diversity-signal}).
Among Base-passing programs, modal and non-modal forms survived Extra tests at
rates within 1.4 points of each other ($\Delta{=}0.06$ points [$-1.4$, 1.4]).
Configurations with more diverse forms had slightly higher Extra-failure rates
($\rho{=}0.13$ [0.02, 0.23]), but the association did not survive adjustment
for Base pass rate (partial $\rho{=}0.07$ [$-0.04$, 0.18]) or for task
(within-task $\rho{=}0.02$ [$-0.10$, 0.13]).
In the five-model replication, it survives adjustment for Base pass rate
(partial $\rho{=}0.13$ [0.06, 0.20]) but not for task (within-task
$\rho{=}0.04$ [$-0.02$, 0.11]), and modal and non-modal forms again survive at
similar rates ($\Delta{=}-0.01$ [$-1.4$, 1.5]).
The association is therefore between tasks: tasks whose passing programs take
many forms also tend to fail Extra tests, but within a task, more diverse
configurations are not detectably more error-prone.
Task-level factors such as specification ambiguity may drive both.

Configurations whose Base-passing programs all shared one form still failed
Extra tests 10.7\% of the time: generation can be repeatably wrong.
When any Base-passer failed Extra tests, all of them failed in 53.3\%
[34.7, 72.0] of configurations that have at least two distinct Base-passing
forms (five-model replication: 41.5\% [27.8, 56.0]; post hoc uniformity check).

\subsection{RQ4: Evaluating mitigation policies}
\label{sec:rq4}

RQ4 demonstrates that \sameeval{} can evaluate mitigation policies, on the two
original models (GPT-4o-mini, Claude Sonnet 4.5); the expansion models are
scored on the overlay only.
On static prompts, replaying a stored program is the ceiling; \skyt{} is
evaluated as a policy that still regenerates.
RQ2 validated the fingerprint's ``same'' on raw pairs; repaired programs were not labeled.

\subsubsection{Policies and results}
\label{sec:rq4-policies}
The policies are raw generation, first Base-certified cache, Base Consensus
cache, and \skyt{}; each sees only Base tests at selection time, and Extra
tests are reserved for evaluation.
On held-out generations, \skyt{} raises Plus \sameat{} from 66.1\% to 83.1\%
($+17.0$ points [14.5, 19.6]) while Plus pass rises from 83.3\% to 85.9\%
($+2.7$ [1.7, 3.8]) (Table~\ref{tab:heldout}, Figure~\ref{fig:arrows}).
(The 66.1\% pre-\sameat{} differs from the RQ4-subset row of
Table~\ref{tab:he-table1}, 65.9\%, because it is computed on the held-out
halves.)
Among generations that pass the Base oracle, Extra-test survival rises from
88.5\% to 89.7\% ($+1.2$ [0.3, 2.3]): repeatability improves without reducing
the chance that an operationally certified output survives unseen tests.
Four configurations have a negative held-out Plus-pass delta (HumanEval/124,
GPT-4o-mini, both temperatures; HumanEval/91, Claude, $T{=}0.0$;
HumanEval/32, GPT-4o-mini, $T{=}0.7$): Extra tests failed after a
Base-authorized commit, so operational certification does not eliminate
repair risk, and the reserved Extra tests are informative.
No configuration has a negative operational (Base-certified) \sameat{} delta.

\subsubsection{Where the effect comes from}
\label{sec:rq4-mechanism}
When \skyt{} fires, the typical rewrite is Level-3 substitution of the
entry-point AST with the train Certified Consensus function
(Table~\ref{tab:level-ablation}).
The live transformer has no separate Level-1 pass, so L1-only equals raw.
Level 2, oracle-gated statement removal, moves Plus \sameat{} by $+0.3$
points [0.1, 0.5] and transforms 0.04 of 10 test programs per split: statement
removal does not account for the lift.
Live \skyt{} (Level 2 then Level 3) transforms 1.7 of 10 programs and gains
$+17.0$ points.
A Level-3-only replay, without Level-2 simplification or live rollback,
transforms 9.5 of 10 programs and gains $+18.1$ [15.5, 20.8]; it is not a strict
subset of live \skyt{}.
Canonical substitution can produce a lift at least as large as live \skyt{};
live \skyt{} is the more conservative policy.
Level 3 does not invent an algorithm: it pastes a stored verified function.
The dominant source of zero gain is the absence of a certified train consensus
on the Base oracle-split design (29 of 656 configurations).
The largest lifts match the mechanism: for HumanEval/83 under GPT-4o-mini at
$T{=}0.7$, pre-\sameat{} is near 0 and \skyt{} rewrites the test slice onto the
train form (post \sameat{} 1.0; Plus pass 29\% $\to$ 100\%); for HumanEval/109
under Claude at $T{=}0.7$, Plus pass is already 100\% and \sameat{} still rises
from 4.9\% to 100\%.

\subsubsection{Robustness}
\label{sec:rq4-robustness}
The lift survives all three rulers ($+14.9$, $+15.4$, $+17.1$ points;
Table~\ref{tab:fingerprint}). These come from a persist replay of the repaired programs, which matches the held-out run in Table~\ref{tab:heldout} ($66.1\rightarrow 83.1$, $+17.0$) to 0.1 points.
Using the full Plus suite during repair yields an almost identical effect
($+17.0$ [14.5, 19.6]; Plus pass $+2.4$ [1.5, 3.5]; certified disagreement
23.2\% $\to$ 3.5\% on 562 configs), so the result does not depend on which
tests \skyt{} sees.
The \sameat{} effect equals the headline at the reported precision; both runs use the same bootstrap seed.
Nested split counts $B\in\{20,50,100,500\}$ move the lift from $+17.1$ (persist replay) to
$+17.3$ points, inside the original interval.

\rqanswer{RQ4}{\sameeval{} separates policies. On static prompts a stored
program is the repeatability ceiling; \skyt{} reaches within about 2 points
of it while still regenerating, is slightly more correct, and gets its
$+17.0$-point lift from canonical substitution, not statement removal.}

\section{The \sameeval{} Protocol}
\label{sec:protocol-steps}

The results above answer four questions about HumanEval+.
Table~\ref{tab:protocol} turns them into a protocol that anyone can apply to
another benchmark, model, or configuration.
Each step states what to do and the evidence in this paper that motivates it;
steps without empirical evidence are marked as design requirements.
The protocol follows the logic of industrial measurement-system analysis:
establish that the measurement is reliable (step~3) and that the ruler
agrees with human judgment (step~6) before drawing conclusions from comparisons (steps~7--8).

\paragraph{What the protocol is not.}
It produces estimates with known precision; it does not certify that a model
or configuration is repeatable.
We propose no pass/fail threshold, because nothing in this study justifies a
particular cut-off; acceptable repeatability depends on how a team reviews,
audits, and ships code.
Nor does the protocol decide which notion of sameness a team should adopt:
step~6 makes that choice explicit and measurable.

\paragraph{Cost and scope.}
The dominant cost is step~3: $N{=}10$ generations per configuration halves the sampling cost of this study while keeping split-half reliability at or above 0.89.
The human calibration in step~6 is per ruler version and language, not per
model; we recommend repeating it when either changes.
The evidence behind steps~3 and 5--8 comes from HumanEval+ only; the steps
themselves are task-agnostic.
Extending the protocol with a step that regenerates under perturbed contexts
is the natural next step (Section~\ref{sec:conclusion}).

\section{Discussion}
\label{sec:discussion}

\paragraph{Two levels of sameness.}
In clone-detection terms~\cite{roy2009clone}, the fingerprint's ``same'' is
approximately Type-2 identity: identifiers renamed, formatting and docstrings
ignored.
Engineers' ``same implementation'' extends toward Type-3: small statement-level
changes such as reordered assignments or an extra temporary.
Both levels are real, and they answer different questions.
At the structural level, which is what diffs, audits, and change control see,
passing regenerations disagree often.
At the implementation level, they agree more.
Pair-weighted over the four RQ4 cells, the fingerprint separates 19.9\% of both-certified pairs; annotator A would call 14.4\% different (95\% CI 10.8--17.6) and annotator B 3.8\% (1.1--6.8) (post hoc). The task-weighted fingerprint rate on the same cells is 23.4\% (Table~\ref{tab:he-table1}, RQ4 subset); the two figures differ in weighting, not in cells.
Models agree on the approach more than on the code.

\paragraph{The shortcuts, revisited.}
For GPT-4o-mini at $T{=}0.7$, copy-first would freeze a passer from a cell whose
certified pairs share a form only 60.0\% of the time, and stop-after-first-pass
would report the 79.7\% pass rate and never the 48.9\% \sameat{}.

\paragraph{Cache and \skyt{}.}
On static prompts, cache is the repeatability ceiling; \skyt{} trades about 2
points of \sameat{} for a small correctness margin.
Caching eliminates regeneration; \skyt{} constrains it.
We do not claim this replay shows \skyt{} is preferable when regeneration is
optional.
\skyt{} is aimed at settings where regeneration remains necessary and replay
is unavailable or unsafe---changed context, incremental edits, model updates,
or a policy that forbids replaying a stored file---and those settings are not
this experiment.
How often a train canon exists also depends on the operational oracle:
relaxing it from Plus to Base raises canon availability from 569 to 627 of 656
configurations, while held-out repeatability is essentially unchanged.

\section{Implications}
\label{sec:implications}

\paragraph{For practitioners.}
If structural repeatability matters, use $T{=}0$ where the provider allows it:
\sameatc{} reaches 96.4\% (Haiku 4.5), and the step from $T{=}0$ to $T{=}0.7$ moves Plus pass by at most 0.8 points (every CI within $\pm$2.4).
Choose models on repeatability as well as correctness: at $T{=}0$, Haiku 4.5 and
Luna pass equally often but differ by 15.3 points among passers.
Do not assume the highest-passing model is the most repeatable: Sonnet 5 passes
92.9\% of tasks yet reaches 66.3\% \sameat{}, at a setting users cannot change.
When regeneration is optional, replay a stored program.

\paragraph{For benchmark designers and researchers.}
Report \sameat{} alongside pass@$k$, following the protocol in
Section~\ref{sec:protocol-steps}.
State which notion of sameness is measured: structural identity (this paper)
and implementation-level sameness (human judgment) differ, and engineers
themselves draw the second line differently.

\paragraph{For tool builders.}
Canonical substitution is the mechanism that produces structural
repeatability; statement removal does not.
Whether constraining form beats replay when regeneration is required is the
open question (Section~\ref{sec:conclusion}).

\section{Threats to Validity}
\label{sec:threats}

\paragraph{Construct.}
Fingerprint identity is the operational definition of same form; it is not
observational equivalence, algorithm identity, or semantic equivalence.
Engineers agreed with the fingerprint's ``same'' (63 and 64 of 64 pairs), but
the fingerprint is stricter than their notion of same implementation
(unweighted sample sensitivity 63--78\%; reweighted, 83.2--93.1\%), and
they agree with each other at a fair-to-moderate level (sample
$\kappa{=}0.41$, 95\% CI 0.26--0.55).
Annotator A is the first author.
The human sample is 128 raw pairs from two models; repaired programs were not
labeled.
The fingerprint was not changed after labeling.
Three computational rulers preserve the gap and the \skyt{} lift.

\paragraph{Internal.}
The 10/10 split prevents selecting the canon from the evaluation generations.
Plus pass includes Base tests, so it is not a fully unseen correctness metric;
Extra tests are unseen, and Extra survival is reported separately.
RQ4 uses two models; replicating the policy comparison on the expansion models
is future work.
The expansion models were called through the Batch API and the original two synchronously; model comparisons that cross these groups (for example, Haiku 4.5 versus Sonnet 4.5) cannot separate model from serving mode.
Post hoc analyses are labeled as such.

\paragraph{External.}
HumanEval+ only (single-function Python tasks, likely in pretraining data);
five closed models from two API vendors, no open-weight model; two
temperatures plus provider-default sampling for Sonnet 5; no dose--response
claim.
Short functions leave little room for structural variation, so we expect more
scatter on larger tasks, but we did not test it.
The protocol's evidence comes from HumanEval+ only.
The overlay applies unchanged to any benchmark with an executable oracle;
MBPP+~\cite{liu2023evalplus} uses the same EvalPlus harness and is the
immediate next task set.
We make no claim about safety-critical readiness.
The model-based embedded motivation (Section~\ref{sec:motivation}) is not
evaluated here: the tasks are Python functions, not code generated from
Simulink models, and we do not assess tool qualification.

\paragraph{Exploratory analyses.}
RQ3 hypotheses were specified before computation but after a related
distinct-forms count had been seen.
Extra survival is a proxy for hidden correctness.
The five-model replication has about twice the configurations; its partial
correlation excludes zero while its within-task correlation does not, which
we read as a small between-task association.

\paragraph{Statistical conclusion.}
Inference is a cluster bootstrap by task with paired CIs for effects; cells
share tasks, so per-cell intervals are not independent.
\sameat{} is a U-statistic of order 2, not a squared pass rate; we do not treat
$p^2$ as a null.
Model-pair comparisons (12 pairs, two metrics) use unadjusted 95\% intervals; the headline 15.3-point \sameatc{} gap has interval [11.0, 19.7], far from zero.

\section{Conclusion}
\label{sec:conclusion}

Tests do not say whether the next passing program is the same code.
On HumanEval+, Plus pass and \sameat{} are far apart (86.4\% versus 67.7\%
across four models), temperature lowers \sameat{} by 11.0 to 28.0 points
while Plus pass moves by at most 0.8 points, and \sameat{} separates models that
pass@$k$ cannot.
Engineers agree with the fingerprint's ``same'' but judge some structural
differences to be the same implementation: models agree on the approach more
than on the code.
Within a task, form diversity shows no detectable association with hidden-test failure
(exploratory).
\sameeval{} separates mitigation policies: a stored program is the ceiling on
static prompts, and \skyt{}'s lift comes from canonical substitution.
The eight-step protocol packages these findings so that repeatability can be
measured and reported on other benchmarks and configurations.

\sameeval{} leaves one question open by design.
When regeneration is required---changed context, incremental edits, model
updates---does constraining form toward a verified canon beat replaying a
stored program?
Answering it requires a regeneration track for \sameeval{}: the same tasks
under perturbed contexts, where a stored program may no longer apply.

A second direction concerns \skyt{} itself.
Today it keeps only the most reproduced verified form and discards the other
passing draws.
A natural extension would use that diversity instead of discarding it:
selecting among, and possibly combining, verified forms from several draws to
build the canon toward which later regenerations converge.
Our results bound what to expect.
Within a task, form diversity shows no detectable association with hidden-test failure (RQ3), so
diversity is material to build from, not a correctness signal, and every
combined form still needs the oracle.
Any such extension should be judged with \sameeval{} against a stored program,
the ceiling on static prompts (RQ4), and in the regeneration settings where
replay is unavailable.
